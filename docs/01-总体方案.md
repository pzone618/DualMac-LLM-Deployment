# 01｜双 Mac 本地 AI 集群：需求与总体部署方案

> **版本** v1.0｜**日期** 2026-11-16｜**目标**：一份总体架构文档 + 两台机器各自的部署操作手册 + 一套可修改的 Bash 脚本。  
> **适用设备**：Mac mini M4 Pro 24GB、Mac mini M6 24GB、Thunderbolt 5 线缆。  
> **部署状态**：已依据官方资料编写，**尚未在用户真实设备完成执行验证**。

## 1. 需求说明

### 必须满足（P0）

1. 两台 Mac 分别通过 Apple Metal 运行 GGUF 模型（Independent 模式）。
2. 两台 Mac 通过 Thunderbolt Bridge 互联，在 `llama.cpp` RPC 模式下协同推理同一个大 GGUF 模型（Distributed 模式）。
3. 同一台主控机器统一查看模型目录、向 Hugging Face 下载模型、在 M4/M6 两个节点运行模型。
4. 提供 OpenAI-compatible HTTP API、启动/停止、健康检查、日志和基本故障排查。
5. 构建版本可追溯：主控与工作节点使用**完全相同的 llama.cpp commit**。

### 后续增强（P1）

- `llamactl` Web Dashboard、HF 搜索下载与动态实例管理。
- 统一 API Gateway / Open WebUI；模型分组、模型量化管理。
- 自动切换策略、任务排队、性能基准与监控。
- launchd 开机启动（先不启用，待安全性和稳定性验证后再做）。

**成功标准**：能在 M4 Pro 上依次切换两种模式；独立模式的两台模型都返回 `/health` HTTP 200；分布式模式的 RPC 工作节点在 M6 运行，M4 上的 `/health` 和实际推理请求成功；模型文件能统一清点；日志可定位故障。

## 2. 重要的硬件限制（校订）

| 硬件 | 确认情况 | 含义 |
|---|---|---|
| M4 Pro 2024 Mac mini | Thunderbolt 5 | 主控设备 TB5 可用 |
| 标准 M6 2026 Mac mini | **Thunderbolt 4** | 另一端连接按 TB4 能力协商，线缆不会升级端口 |
| 雷电 5 线缆 | 兼容较低版本的端口 | 可以作为 Thunderbolt Bridge 的物理线缆 |
| Apple RDMA over Thunderbolt | 双方需支持 Thunderbolt 5 且系统满足条件 | **本组合不按 RDMA 部署** |

Apple 规格来源：
- M6: https://support.apple.com/en-us/128108
- M4 Pro: https://support.apple.com/en-us/121555
- Apple TN3205: https://developer.apple.com/documentation/technotes/tn3205-low-latency-communication-with-rdma-over-thunderbolt

**结论**：使用 **TCP over Thunderbolt Bridge + llama.cpp RPC**。禁止把两台 24GB 理解成一台 48GB 连续统一内存；真实模型上限低于物理内存和，具体还受 macOS、KV Cache、缓冲区、RPC 传输与量化方式制约。

## 3. 角色与拓扑

```text
                       管理者 / 应用客户端
                               |
                        M4 Pro 本机访问
                               |
                 +-------------+-------------+
                 | M4 Pro（主控）10.77.0.1    |
                 | HF 下载、模型清单、模式管理 |
                 | llama.cpp/Metal             |
                 | Independent API :8081       |
                 | Distributed API :8083       |
                 +-------------+-------------+
                               |
             Thunderbolt 5 线缆 + IP over TB (TCP)
                               |
                 +-------------+-------------+
                 | M6（工作节点）10.77.0.2     |
                 | llama.cpp/Metal             |
                 | Independent API :8082       |
                 | RPC Worker TCP :50052       |
                 +---------------------------+
```

端口与 IP 是**建议配置**，以 `config/cluster.env` 为准。主控的 API 绑定到 `127.0.0.1`，M6 独立 API 和 RPC 只绑定到专用 Thunderbolt IP。不要将 RPC 服务暴露到互联网、公司网络或不可信局域网。

## 4. 模式与资源独占

### A. Independent（两台独立）

- M4：运行 `llama-server -m ... --host 127.0.0.1 --port 8081`。
- M6：运行 `llama-server -m ... --host 10.77.0.2 --port 8082`。
- 适合：双服务并行、一个模型用于编码、另一个模型用于英语学习、不同 API 消费者。
- Web UI 可在第二阶段接入两个 OpenAI 兼容 endpoint。

### B. Distributed（两台协同推理）

- M6：关闭独立模型服务，启动 `ggml-rpc-server -H 10.77.0.2 -p 50052 -c`。
- M4：关闭独立模型服务，启动 `llama-server -m ... --rpc 10.77.0.2:50052 ... --port 8083`。
- 模型 GGUF 文件**由 M4 读取**，权重按当前 llama.cpp 的内存分配策略卸载到设备，M6 不一定需要下载同一份 GGUF；启用 RPC 本地张量缓存后，M6 可缓存远程张量，加快重复加载。
- 初次只用小模型进行连通性测试；真正验证双机内存收益需要一个单机难以容纳、双机有望容纳的 GGUF（如约 27B/32B Q4），并观测两端内存压力。

**互斥策略**：本包 `cluster-mode.sh` 在切换时会停掉由本包管理的旧 tmux 推理会话，避免并行内存争用。它**不会**杀掉你原有 LM Studio / Ollama / 其他 llama.cpp 进程；这些必须自行先关闭。

## 5. 模型管理策略

**第一阶段：统一命令行模型管理**（可直接执行，较可靠）。

- M4 为主控：`scripts/model-manager.sh download m4|m6 repo/name file.gguf`。
- 两台独立保存本地 GGUF 到 `~/AI/models/<repo-owner>__<repo-name>/<file>.gguf`。
- M4 执行 `scripts/model-manager.sh inventory`，通过 SSH 汇总两台的文件列表。
- 先用明确文件名下载单一 GGUF，不要无意下载同一仓库所有量化版本。
- 分片 GGUF 必须下载仓库里的全部分片，并向 llama.cpp 传入**第一片路径**；本包默认 `download-model.sh` 仅处理单文件 GGUF。大型分片模型请按 Hugging Face 文档使用 `hf download --include`。
- Gated/私有模型：在实际需要下载的机器执行 `~/AI/.venv/bin/hf auth login`，并遵守模型许可证，**不要把 Token 写进 `.env`**。

**第二阶段：llamactl**（作为 UI/模型生命周期增强，非第一阶段的唯一依赖）。

- 先到 `https://github.com/lordmathis/llamactl/releases/latest` 下载适合 macOS arm64 的官方构建，核对版本、发行产物和校验值后运行。
- 在 M4 上打开项目提供的 Dashboard，先管理一个单机实例。
- 再核实当前版本对**现有外部 llama-server 端点**的接入方式；若支持，再接入 M6 和 Distributed API；如不支持，就把已运行的端点交给 Open WebUI / 自建轻量 Gateway 汇聚，而不是将它们当作能被 llamactl 直接管控的远端进程。
- 避免同时让 llamactl 和本包脚本管理**同一端口、同一进程**。

项目：
- llama.cpp: https://github.com/ggml-org/llama.cpp
- RPC: https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md
- llamactl: https://github.com/lordmathis/llamactl
- Hugging Face CLI: https://huggingface.co/docs/huggingface_hub/guides/cli
- Cluster 脚本参考: https://github.com/riozilla/mac-thunderbolt-llama-cluster

## 6. 部署顺序（严格执行）

1. **双机硬件盘点**：`uname -m`、`sw_vers`、`system_profiler SPHardwareDataType`、`system_profiler SPThunderboltDataType`；分别确认机型、版本、磁盘可用空间。
2. **物理连接**：TB5 线缆连接两台 Mac 后部 Thunderbolt 接口；系统设置 → 网络 → Thunderbolt Bridge。
3. **IP 配置**：M4 `10.77.0.1/24`；M6 `10.77.0.2/24`；不配置默认网关/DNS，以免抢占正常互联网路由。确保与现有 LAN/VPN 网段不冲突。
4. **SSH**：在 M6 的系统设置中启用 Remote Login；在 M4 设置 SSH 公钥并验证 `ssh <M6_USER>@10.77.0.2`。不同用户名是正常情况。
5. **拷贝同一份部署包**到两台的 `~/AI/dual-mac-cluster/`，都复制 `.env.example → .env` 并修改。
6. **锁定版本**：先在 M4 `./scripts/bootstrap.sh`，记录 `git -C ~/AI/llama.cpp rev-parse HEAD`；两台 `.env` 的 `LLAMA_CPP_REF` 填此完整 SHA，再在两台分别重跑 bootstrap/编译。避免一天内 master 更新导致 RPC 不匹配。
7. **模型**：在 M4 下载测试 GGUF；独立模式还要在 M6 下载。运行两台 `--version` 核实构建。
8. **独立模式**：在 M4 执行 `./scripts/cluster-mode.sh local`；观察日志、检查健康和实测推理。
9. **分布式模式**：在 M4 执行 `./scripts/cluster-mode.sh distributed`；检查 RPC 端口、日志、健康和实测推理。
10. **大模型测试**：修改 `DISTRIBUTED_MODEL_REPO/FILE` 并下载对应 GGUF；分布式重新启动，记录内存与速度。
11. **控制台**：在核心模式成功后再接入 llamactl/Open WebUI，最后考虑自动启动。

## 7. 标准验收表

| 验收项 | 命令/观察 | 通过条件 |
|---|---|---|
| Thunderbolt IP | `ping -c 4 10.77.0.2` | 低丢包，路由确走 TB 接口 |
| SSH | `ssh <M6_USER>@10.77.0.2 whoami` | 返回 M6 用户名，无交互密码 |
| 编译版本一致 | `git -C ~/AI/llama.cpp rev-parse HEAD` | 两台一致 |
| M4 local | `curl -i http://127.0.0.1:8081/health` | HTTP 200 / status ok |
| M6 local | `curl -i http://10.77.0.2:8082/health` | HTTP 200 / status ok |
| M6 RPC | `nc -G 2 -vz 10.77.0.2 50052` | TCP 可连接 |
| 双机推理 | `curl -i http://127.0.0.1:8083/health` | HTTP 200 / status ok |
| 实际生成 | 调用 `/v1/chat/completions` | 正常返回非空内容 |
| 服务切换 | `cluster-mode.sh local / distributed / status / stop` | 会话状态与模式相符 |
| 模型清单 | `model-manager.sh inventory` | 显示两台 GGUF 路径 |

**注意**：仅凭 `/health` HTTP 200 **不能证明远端 GPU 实际参与计算**。在分布式启动日志中检查 RPC 设备枚举、权重放置和执行活动，并比较两端 Activity Monitor 的内存使用量。

## 8. 风险与回退方案

- **RPC 安全**：官方明确将 RPC 标为实验性且不安全，**只在专用、可信、隔离的 Thunderbolt 网络启用**；不要开启公网端口映射，建议先不设开机常驻。
- **版本漂移**：如果模型、RPC 或命令行选项异常，先核对两个 commit 一致；脚本仅对应文档核对时的 CLI 风格。
- **macOS 本地网络授权**：独立后台进程可能触发 Local Network 权限问题；如 SSH + tmux 的 M6 RPC 连接失败，先在 M6 交互式 Terminal 直接执行 `run-m6-rpc.sh` 排除后台权限因素。
- **模型爆内存**：先停掉 LM Studio/Ollama；将 `CTX_SIZE` 调小；选择更小量化；在模型确实需要分布式时再启用 RPC。
- **模式切换失败**：`./scripts/cluster-mode.sh stop`；分别在 M4/M6 查看 `tmux ls` 与 `~/AI/logs`；回退到单机独立服务。
- **下载失败**：检查 `hf auth whoami`、许可证、代理、磁盘空间与 CDN 连通性；无需重新编译整个 llama.cpp。

## 9. 后续扩展设计

未来如确实需要长期运行：

```text
FastAPI Cluster Controller（可选）
    ├─ Model Registry (SQLite：repo/revision/quant/file/hash/license)
    ├─ Scheduler (independent/distributed/queue)
    ├─ Remote Agent (SSH or authenticated mTLS agent)
    ├─ Launcher (llama.cpp process lifecycle)
    ├─ Metrics (RAM / tokens/s / TTFT / load time)
    └─ Gateway (OpenAI-compatible routing & authentication)
```

当前版本不增加 Redis、Kubernetes、数据库服务或 Docker，保持 Apple Metal 原生运行，减少实验变量。等 TCP/RPC 稳定后才有必要评估复杂化。
